# 자율 출근제 개념 — 이 앱이 쓰는 낱말

> **초안입니다.** 팀장 검토 전이고, 마지막 절「아직 안 갈라진 것」은 결정이 남아 있습니다.

## 왜 이 문서가 있나

설계 대화가 반복해서 헛돌았습니다. 같은 낱말이 세 가지를 뜻했기 때문입니다.

- **"정산기간"** — 종류(주/월)인지, 구체적 구간(7/1~7/31)인지, 마감 단위인지
- **"확인 필요"** — 본인 대시보드 카드인지, 팀 현황 건수인지, 알림 목록인지
- **"52시간"** — 기준인지 상한인지 (기준은 40시간입니다)

그래서 갈라 적습니다. 각 낱말은 **① 뜻 ② 사용자에게 어떻게 보이나 ③ 코드 어디 ④ 헷갈리는 지점** 순서입니다.

## 1. 자율 출근제란 (처음 보는 분께)

정식 이름은 **선택적 근로시간제**(근로기준법 §52)입니다.

일반 근무제는 "매일 9시 출근, 6시 퇴근"처럼 **시각**이 정해져 있습니다.
자율 출근제는 그 시각을 근로자가 정합니다. 대신 **정산기간 총 근무시간**을 맞춥니다.

```
일반 근무제    매일 8시간 × 23일   ← 하루 단위로 지킨다
자율 출근제    7월에 184시간       ← 총량만 맞추면 된다
               (어떤 날 11시간, 어떤 날 5시간이어도 된다)
```

**도입 조건** — 취업규칙에 근거를 두고, 근로자대표와 **서면합의**로 다음을 정해야 합니다(§52①).

| 서면합의 항목 | 이 앱의 설정 |
|---|---|
| 대상 근로자 범위 | (앱 밖) |
| 정산기간 | 근태 설정 → 정산기간 |
| 정산기간의 총 근로시간 | 근태 설정 → 소정근로 산정 방식 |
| 의무근로시간대 | 근태 설정 → 의무근로시간대 |
| 선택 가능 시간대 | 근태 설정 → 선택적 근로시간대 |

> **이 앱이 하지 않는 것** — 수당 계산을 하지 않습니다. 시간만 정확히 남기고,
> `전사 집계` 의 CSV를 급여 시스템에 넘깁니다.

## 2. 시간 네 가지 — 가장 많이 섞이는 곳

| # | 낱말 | 값 | 성격 |
|---|---|---|---|
| ① | **법정근로시간** | 1주 **40시간** · 1일 8시간 | 법이 정한 기준 (§50) |
| ② | **소정근로시간** | 7월 **184시간** | 당사자가 정한 것 (§2①7호) |
| ③ | **연장근로 한도** | 1주 **12시간** | 합의로 늘릴 수 있는 최대 (§53) |
| ④ | **1일 상한** | **12시간** | 법정 아님. 회사가 정한 건강권 관리 기준 |

### ① 법정근로시간 — 넘으면 "연장근로"가 된다

1주 40시간, 1일 8시간(§50). 이걸 **넘긴 시간이 연장근로**이고 통상임금의
50% 이상을 가산해야 합니다(§56).

자율 출근제에서는 **개별 주가 아니라 정산기간을 평균해서** 봅니다. 그래서
어떤 주에 50시간, 다른 주에 30시간을 일해도 평균이 40시간 이하면 연장근로가
0입니다. **이게 이 제도의 요점이고 이 앱이 존재하는 이유입니다.**

- 화면: 대시보드 `법정초과 31시간 58분`
- 코드: `legalWeeklyMinutes` — **설정이 아니라 코드에 박혀 있습니다**
  ([db/access.ts:168](../db/access.ts#L168) `40 * 60`). 법이 정한 값이라 회사가 못 바꿉니다
- 계산: `overtimeMinutes = 누적 − (정산기간 주수 × 40시간)`

### ② 소정근로시간 — 내가 채워야 하는 양

근로계약·서면합의로 **정한** 근로시간입니다(§2①7호). 이 앱의 기본 산정은
`영업일 수 × 1일 소정근로(8시간)`입니다. 7월은 영업일 23일이라 **184시간**.

- 화면: 대시보드 `소정근로 184시간` · `남은 시간`
- 코드: `targetMinutes` ([settle.ts](../lib/attendance/settle.ts))
- 설정: `target_calc_method` — `business_days`(기본) 또는 `fixed`(기간당 고정 시간)
- 승인된 휴가는 여기서 **차감**됩니다 (연차 1일 = 8시간)

세 값을 갈라 읽어야 합니다. 지금 코드의 `targetMinutes` 는 **셋째**입니다.

```
scheduledTargetMinutes   원래 소정근로              184시간
approvedLeaveMinutes     승인된 휴가                  8시간
requiredWorkMinutes      실제로 채워야 할 근무시간    176시간   ← targetMinutes
```

⚠ **아직 앞의 두 값이 화면에 없습니다.** `targetMinutes` 가 이미 차감된 값이라
"원래 소정근로가 얼마였는지"를 알 수 없습니다. 필드를 **추가**해야 하고,
`targetMinutes` 의 의미는 바꾸면 안 됩니다 — 마감 스냅샷 6개 중 하나라서
의미가 바뀌면 마감된 모든 기간에 거짓 변경 경보가 뜹니다.

> **못 채우면 법 위반인가?** 아닙니다. 소정근로 미달은 근로계약 문제이고
> 임금 공제·복무 사안입니다. 법 위반은 ①③을 **넘겼을 때** 생깁니다.

### ③ 연장근로 한도 — 넘으면 위법

당사자 합의로 1주 12시간까지 연장할 수 있습니다(§53①). 40 + 12 = **52시간**이
**일반적인 선택적 근로시간제의 법정 상한**입니다. 자율 출근제에서는 이것도
정산기간 평균으로 판단합니다.

- 화면: `이대로면 주 평균 52시간 초과` · `법정 한도 52시간 초과`
- 코드: `maxAvgWeeklyMinutes` — `limit_minutes_per_week` 설정(3120분 = 52시간)
- 설정 가능한 이유: 12시간 연장은 **합의 사항**이라 회사가 더 낮게 정할 수 있습니다

> **52는 기준이 아니라 상한입니다.** 기준은 40이고, 40~52 구간은 "연장근로라
> 수당을 줘야 하는" 구간이며, 52를 넘으면 위법입니다.

> ⚠ **이 앱이 계산하지 않는 예외** — 특별연장근로 인가(§53④)나 근로시간 특례업종
> (§59)처럼 별도 인가·특례로 52시간을 넘길 수 있는 경우는 판정에 반영하지
> 않습니다. 그런 인가를 받은 기간에는 이 앱의 `법정 한도 초과` 표시를 그대로
> 위법으로 읽으면 안 됩니다.

### ④ 1일 상한 — 법정 아님

하루에 이 이상 일하면 `1일 상한 초과` 로 걸립니다. **법정 기준이 아닙니다** —
자율 출근제는 1일 8시간에 묶이지 않으므로, 이건 건강권 관리를 위해 회사가
정하는 값입니다.

- 코드: `dailyLimitMinutes` (`daily_limit_minutes`, 기본 720분 = 12시간)
- `null` 로 두면 검사하지 않습니다
- 화면: 일별 근무의 `1일 상한 초과` 태그, `남은 영업일로는 채울 수 없습니다` 판정

### 넷을 한 줄로

```
소정근로(184h)  ← 내가 채워야 하는 양      (못 채우면 계약 문제)
법정 총량(177h) ← 넘으면 연장근로 + 수당    (§50)
한도 총량(230h) ← 넘으면 위법              (§53)
1일 상한(12h)   ← 회사 기준                (법정 아님)
```

## 3. 정산기간 세 갈래

"정산기간"이라고 말할 때 셋 중 하나입니다. **이 셋을 섞으면 대화가 헛돕니다.**

| # | 무엇 | 어디 | 단위 |
|---|---|---|---|
| ① | **종류** — 주 단위냐 월 단위냐 | `settlement_period` 설정 | 조직 |
| ② | **구체적 구간** — `2026-07-01 ~ 2026-07-31` | [period.ts](../lib/attendance/period.ts) `resolvePeriod()` | 계산할 때마다 |
| ③ | **마감 단위** | `settlement_periods` 테이블 | 조직 |

### ① 종류

`week` 또는 `month`. 서면합의 항목이므로 HR이 `근태 설정` 에서 정합니다.
법은 **1개월 이내**만 허용합니다(신상품·신기술 연구개발은 3개월).

### ② 구체적 구간

**저장되지 않습니다.** 날짜를 넣으면 매번 계산됩니다.

```
resolvePeriod("2026-07-15", { kind: "month", ... })  →  7/1 ~ 7/31
resolvePeriod("2026-07-15", { kind: "week", weekStartDay: 1 })  →  7/13 ~ 7/19
```

대시보드 상단의 `← 이전  7/1(수) ~ 7/31(금)  다음 →` 이 이것입니다.

**이 구간이 곧 개인의 계산 구간은 아닙니다.** 중도 입사·퇴사자에게는 여기에
근로관계 존속기간을 교집합한 **개인 집계기간**이 계산에 쓰입니다 — §4를 보세요.
조직 정산기간이 직접 정하는 것은 **마감 단위**입니다.

### ③ 마감 단위

`settlement_periods` 테이블. `orgId + periodStart` 가 유니크라 **조직 단위**입니다.
유예 3일(`close_grace_days`) 뒤 자동 마감되고, 사람별 스냅샷이 동결됩니다.

## 4. 재직기간 — 개인 집계·적용기간

**정산기간이 개인별로 짧아지는 것이 아닙니다.** 정산기간은 근로자대표와 서면합의로
정한 **조직의 것**이고(§52①2호), 개인에게 달린 것은 그 기간 중 어디까지가 이
사람에게 적용되는가입니다. 그래서 두 낱말로 갈라 씁니다.

```
organizationSettlementPeriod   서면합의한 제도상 정산기간        7/1 ~ 7/31
employmentApplicablePeriod     ∩ 근로관계 존속기간             7/20 ~ 7/31
                               = 개인 집계·적용기간
```

### 무엇에 어느 기간을 쓰나

| 값 | 쓰는 기간 |
|---|---|
| 실근무 집계 | **개인 집계기간** |
| 개인 소정근로 목표 | **개인 집계기간** |
| 법정근로 총량 (`applicableStatutoryMinutes`) | **개인 집계기간** ÷ 7 × 40h |
| 법정 한도 총량 (`applicableLimitMinutes`) | **개인 집계기간** ÷ 7 × 52h |
| 마감 단위 | **조직 정산기간** |

### 왜 법정 계산의 분모까지 개인 집계기간인가

**근로관계가 존재하지 않았던 기간까지 평균의 분모에 포함하면, 실제 근로기간의
평균 근로시간과 연장근로 한도가 인위적으로 희석됩니다.**

7월 20일 입사자가 영업일 10일에 하루 12시간씩 = 120시간 일한 경우
(주 70시간 페이스):

| | 조직 정산기간 분모 (4.43주) | 개인 집계기간 분모 (1.71주) |
|---|---|---|
| 법정 총량 | 177시간 9분 | 68시간 34분 |
| **연장근로** | **0시간** | 51시간 26분 |
| 한도 총량 | 230시간 17분 | 89시간 9분 |
| 주평균 | 27시간 6분 | 70시간 |
| 52시간 판정 | ⚪ 안 걸림 | 🔴 위법 |
| §53 연장근로 허용량 | 53시간 9분 | 20시간 35분 |

조직 분모를 쓰면 12일 재직한 사람에게 **53시간의 연장근로 여유**가 생기고
가산수당 대상 시간이 **0**이 됩니다.

### 규칙

- 필드: `users.hiredAt` · `users.resignedAt` (둘 다 nullable, 퇴사일 **포함**)
- `hiredAt` 은 **근로관계 시작일**입니다. 정규직 전환일이 아닙니다 — 인턴도
  근로자이므로 전환일을 넣으면 그 기간이 집계에서 빠집니다
- 비례 기준은 **소정근로일 수**입니다 (역일 아님). 역일로 하면 금요일 입사자와
  월요일 입사자의 목표가 주말 때문에 뒤바뀝니다
- **퇴사자에도 대칭으로 적용됩니다.** 3/16 입사와 3/16 퇴사는 집계기간 길이가
  같고 법정 총량·한도도 같습니다
- 교집합이 비면 0이 아니라 **"재직 기간이 아닙니다"** 입니다. 0으로 두면
  "안 일했다"로 읽혀서 없는 미달이 생깁니다
- 코드: `applicableStart` · `applicableEnd` · `employed` · `partialEmployment`
- 검사: [employment.guard.test.ts](../lib/attendance/employment.guard.test.ts)

## 5. 하루를 어떻게 읽나

원본에서 실근무까지 이렇게 갑니다.

```
태그(tag)     사원증·지문 단말이 찍은 시각 1건. append-only, 절대 지우지 않는다
  ↓
세션(session) in~out 한 쌍. 하루에 여러 개일 수 있다
  ↓
구간          겹치는 세션을 합친 것 (앱 체크인 + 사원증 기록의 이중 계산을 막는다)
  ↓
실근무(work)  구간마다 (길이 − 그 구간의 휴게) 를 구해서 **더한 값**
```

| 낱말 | 뜻 | 주의 |
|---|---|---|
| **태그** | 단말이 남긴 시각 1건 | 지문 단말은 in/out 구분 없이 찍는 경우가 많다 |
| **세션** | 근무 한 구간 | 앱 체크인과 사원증 기록이 겹치면 합쳐진다 |
| **실근무** | **구간별로** 휴게를 빼서 합한 값 | 소정근로·법정초과·주평균이 전부 이 값이다 |
| **체류** | **첫 태그 ~ 마지막 태그** (사이 공백 **포함**) | 표시용이다. 집계에 안 쓴다 |
| **휴게** | 각 구간 길이에 따라 자동 차감 | 4시간↑ 30분, 8시간↑ 60분. 여러 조건이 맞으면 **가장 큰 것 하나만** |

### 실근무는 "체류 − 휴게"가 아닙니다

세션 경로에서는 **구간마다 따로** 계산해서 더합니다
([sessions.ts:230-238](../lib/attendance/sessions.ts#L230-L238)).
보정이 하루를 한 구간으로 덮어쓴 경우에만 `체류 − 휴게` 가 됩니다
([compute.ts:130-134](../lib/attendance/compute.ts#L130-L134)).

```
오전 09~12 (3h) + 저녁 19~21 (2h)

실근무   구간별  3h − 0분(4h 미만) + 2h − 0분  =  5시간
체류     09:00 ~ 21:00                        = 12시간   ← 집계에 안 쓴다
```

**이게 이 앱의 계산 엔진 핵심입니다.** 체류를 근무로 읽으면 사이 7시간까지
일한 것이 됩니다.

실제로 계산해서 확인한 값입니다 (휴게 4시간↑ 30분, 8시간↑ 60분):

| 근무 모양 | 실근무 | 체류 | `체류 − 휴게` 라면 |
|---|---|---|---|
| 연속 6시간 (09~15) | 5시간 30분 | 6시간 | 5시간 30분 (같다) |
| 3h + 3h (09~12, 19~22) | **6시간** | 13시간 | 12시간 ❌ |
| 3h + 2h (09~12, 19~21) | **5시간** | 12시간 | 11시간 ❌ |
| 연속 10시간 (09~19) | 9시간 | 10시간 | 9시간 (같다) |
| 5h + 5h (09~14, 16~21) | **9시간** | 12시간 | 11시간 ❌ |

> **주의할 부수효과** — 휴게가 구간별이라 **나눠 일하면 차감이 줄어들 수 있습니다.**
>
> ```
> 연속 6시간   →  실근무 5시간 30분  (휴게 30분)
> 3시간 + 3시간 →  실근무 6시간      (휴게 0분)   ← 각 구간이 4시간 미만
> ```
>
> 같은 6시간인데 **30분 차이**가 납니다. 다만 늘 그런 건 아닙니다 —
> 5h + 5h(30분 × 2 = 60분)와 연속 10시간(60분)은 같습니다.
>
> 법정 휴게(§54)는 근로시간 기준인데 그 계산이 순환이라(휴게를 알아야 근로시간을
> 알고, 근로시간을 알아야 휴게를 안다) 체류를 대리 지표로 쓴 결과입니다.
> 의도된 근사이지만 갈라 적어둘 값이 있습니다.

### 날짜 귀속 기준시각

`day_boundary_hour` = 5. **05:00 이전의 태그는 전날로 귀속됩니다.**
밤 11시에 시작해 새벽 2시에 끝낸 근무가 이틀로 쪼개지지 않게 하는 장치입니다.

### 하루의 상태 (`WorkDayStatus`)

| 상태 | 뜻 |
|---|---|
| `computed` | 정상 계산됨 |
| `adjusted` | 보정이 반영됨 |
| `open` | **오늘 진행 중** (근무 중) |
| `incomplete` | **지난 날에 열린 세션이 남았다** — 퇴근 기록 없음. 집계에서 빠진다 |

`incomplete` 가 남아 있으면 **새 근무를 시작할 수 없습니다.** 먼저 정리해야 합니다.

## 6. 보정과 휴가 — 다른 개념입니다

한 화면에 묶여 있었다가 갈라냈습니다.

| | 보정 | 휴가 |
|---|---|---|
| 뜻 | **실제로 일한 것**을 신고 | **근로 의무를 면제**받음 |
| 소정근로 | 안 바뀜 (실근무가 늘어남) | **줄어듦** (승인된 것만) |
| 승인 | 필요 없음 (본인 신고 + 이력) | **팀장·HR 승인 필수** |
| 화면 | `내 기록 · 보정` | `휴가` |

> 승인 전에는 소정근로가 줄지 않습니다. 그렇지 않으면 본인이 자기 목표를
> 낮출 수 있습니다.
>
> **잔여 연차는 관리하지 않습니다.** 총량을 넣으면 부여·이월·회계연도 기준이
> 전부 따라오고, 그건 휴가 관리 시스템의 영역입니다.

있습니다. 이건 [ui.guard.test.ts](../app/ui.guard.test.ts) 가 강제합니다.

## 8. 한도 판정 두 값

| 값 | 뜻 | 언제 켜지나 |
|---|---|---|
| `exceedsAvgWeeklyLimit` | **이미** 한도를 넘었다 | 정확하지만 늦다. 20~22일째 |
| `willExceedAvgWeeklyLimit` | 남은 날을 **소정근로만** 해도 넘는다 | 확정보다 6~10 영업일 먼저 |

`avgWeeklyMinutes` 의 분모는 **개인 집계기간 전체**입니다. 그래서 기간 중에는
분자만 쌓여서 구조적으로 낮게 나옵니다 — 3월 첫 주에 70시간을 일해도 15시간대로
나옵니다. **기간 중에 이 값을 그대로 보여주면 안심시킵니다.**

⚠ **이름 두 가지가 아직 정확하지 않습니다.**

- `willExceedAvgWeeklyLimit` — "반드시 넘는다"로 읽히지만 조건부입니다.
  `projected*` 를 붙이면 **진짜 외삽값인 `projectedAvgWeeklyMinutes` 와 섞이므로**
  쓰지 않습니다. `exceedsLimitEvenIfScheduledOnly` 쪽을 검토 중입니다
- 이 값은 **엄밀한 하한이 아닙니다.** `remainingBusinessDates` 가 오늘을 포함하는데
  오늘 실적은 이미 `workedMinutes` 에 들어 있어서, 영업일에는 오늘 몫만큼
  높게 잡히고 주말에 내려갑니다 (금요일에 켜졌다 주말에 꺼지고 월요일에 다시 켜짐)

실측(7월, 영업일 23일):

| 페이스 | 사전 경고 | 확정 초과 | 기간말 실제 |
|---|---|---|---|
| 9.5시간/일 | 안 켜짐 | 안 켜짐 | 49시간 20분 (합법) |
| 10.5시간/일 | 16일째 | 22일째 | 54시간 32분 (위법) |
| 12시간/일 | 10일째 | 20일째 | 62시간 19분 (위법) |

## 9. 마감과 스냅샷

```
정산기간 종료 → 유예 3일 → 자동 마감 → 사람별 스냅샷 동결
                                          ↓
                          늦게 온 태그가 들어오면
                          "마감 후 값이 바뀌었습니다"로 드러난다
```

- 스냅샷에 얼리는 것은 **6개 숫자**: 소정근로 · 실근무 · 야간 · 휴일근무 · 법정초과 · 주평균
- 임포트를 막지 않습니다 — 원본은 append-only여야 하고, 막으면 데이터가 유실됩니다.
  대신 공식 기록은 스냅샷을 쓰고 **차이를 눈에 보이게** 만듭니다
- 재마감은 HR만, 사유 필수

## 10. 아직 안 갈라진 것 — 결정이 남았습니다

### 소정근로와 법정 총량의 기준이 다릅니다

- 소정근로 = **영업일 × 8시간**
- 법정 총량 = **역일 ÷ 7 × 40시간**

기준이 달라서 영업일이 많은 달에는 **소정근로를 정확히 채우기만 해도 연장근로가
발생합니다.**

| 월 | 영업일 | 소정근로 | 법정 총량 | 차이 |
|---|---|---|---|---|
| 2월 | 20일 | 160시간 | 160시간 | 0 |
| 5월 | 21일 | 168시간 | 177시간 9분 | 9시간 여유 |
| **7월** | 23일 | **184시간** | 177시간 9분 | **+6시간 51분** |
| **12월** | 23일 | 184시간 | 177시간 9분 | **+6시간 51분** |

4·6·7·9·12월이 여기 걸립니다. 이게 버그인지는 단정할 수 없습니다 — 실무에서
월 소정근로를 영업일 × 8시간으로 잡는 회사도 있고, 그러면 연장근로가 실제로
발생하는 게 맞고 수당을 줘야 합니다. **다만 산정 방식은 회사가 정할 사항입니다.**

### 짧은 집계기간에서는 한도까지 넘깁니다

7월 29일 입사자의 개인 집계기간은 7/29~7/31, 3일 전부 영업일입니다.

```
소정근로 (계약)          24시간      ← 회사가 채우라는 양
법정 총량 (§50)          17시간 9분   ← 넘으면 연장근로
법정 한도 총량 (§53)     22시간 17분  ← 넘으면 위법

→ 소정근로를 정확히 채우면 주평균 56시간 · 한도 초과
```

영업일 밀도가 100%(3일 중 3일)라 어긋남이 한도까지 넘깁니다. 주 단위 정산이면
집계기간에 주말이 포함되어 생기지 않습니다.

### 결정된 것 — 세 값을 독립으로 보존한다

**소정근로에 법정 총량·한도 상한을 자동으로 씌우지 않습니다.**

```
contractTargetMinutes        회사·근로계약 기준 소정근로      (targetMinutes)
applicableStatutoryMinutes   선택근로제 법정근로 총량 (40h)
applicableLimitMinutes       연장근로 포함 법정 한도 (52h)
```

소정근로시간과 법정근로시간은 **성격이 다른 값**입니다. §2①7호로 소정근로 산정은
당사자가 정하는 것이므로, 코드가 상한을 씌우면 그게 곧 회사 정책이 됩니다.
그래서 값을 깎지 않고 **셋을 나란히 보존**합니다.

대신 **HR에게 경고**합니다:

> 현재 설정에서는 소정근로를 모두 채울 경우 연장근로가 발생할 수 있습니다.

### 아직 안 만든 것

- 근태 설정 화면의 위 경고 (`영업일 × 8시간` 을 고를 때 어느 달이 걸리는지)
- 짧은 집계기간에서 소정근로가 **법정 한도**까지 넘길 때의 표시
  (지금은 대시보드가 `채울 수 없습니다` 로만 말하고 위법 위험은 안 말한다)
